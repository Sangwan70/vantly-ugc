# RazorPay Default Gateway — End-to-End Verification Report

**Date:** 2026-09-04
**Scope:** Making RazorPay the default payment gateway, auditing the full checkout → webhook → credit flow against AutoGPT's real production implementation, and making the currency symbol/price display dynamic across the app. Written before any real RazorPay or Stripe keys are entered, as requested.

## Summary

RazorPay is now the default payment gateway (`getActivePaymentGateway()` in `supabase/functions/_shared/razorpay.ts` and `apps/web/app/layout.tsx` both default to `"razorpay"` when `PAYMENT_GATEWAY` is unset, matching AutoGPT's own platform default). A deployment that wants to keep using Stripe still can — every Stripe code path is untouched and reachable by setting `PAYMENT_GATEWAY=stripe` on both the Supabase Edge Function secrets and the web container's env file.

The currency symbol and displayed prices are now dynamic across every pricing surface in the app: the landing page pricing cards, the subscribe page, onboarding plan selection, and both billing dashboards (the light `(dashboard)/billing` page and the dark `(app-dark)/dashboard/billing` page), plus the "Payment via Stripe/Razorpay" label and each billing-history invoice row. They all read from a single source (`useCurrencyDisplay()` in `apps/web/lib/billing/currency-display.ts`), which in turn reads the gateway and INR rate that `layout.tsx` resolves once per request from the `currencies` admin table.

I re-audited the entire flow this session against AutoGPT's actual frontend and backend RazorPay code (not just its API shape, but its real Checkout.js integration and price-display logic), found and fixed five real gaps, and re-verified the whole thing end to end: full TypeScript typecheck of `apps/web` (zero errors), the Deno Edge Functions typechecked with only the two expected Deno-runtime error classes (no others), brace/paren balance confirmed on every edited file, the RazorPay webhook signature verification and idempotency logic traced by hand, and the double-crediting risk from RazorPay's `order.paid`/`payment.captured` event pair specifically checked against RazorPay's own documented payload shape.

## What was fixed this session

Five real issues surfaced during the audit, all fixed:

1. **`billingEnabled` was hardcoded to check only `STRIPE_SECRET_KEY`.** Once RazorPay became the default, a deployment configured only with `RAZORPAY_API_KEY`/`RAZORPAY_API_SECRET` (no Stripe key at all) would have had all billing UI silently hidden. `layout.tsx` now checks the active gateway's own credentials.
2. **Checkout success/cancel navigation was missing for RazorPay.** AutoGPT's real Checkout.js integration navigates the browser after `handler` (success) and `modal.ondismiss` (user closed without paying) fire. Vantly's `open-checkout.ts` now does the same, landing on the same `/billing?status=success` / `?status=canceled` destinations Stripe already uses.
3. **`supabase/deploy.sh`'s manual function list was stale.** It was missing `webhook-razorpay` (would never have deployed via the manual script) and, independent of this work, was already missing `billing-history` and `cancel-subscription`. All three are now listed. Note the GitHub Actions deploy workflow (`.github/workflows/deploy.yml`) was never affected by this — it auto-discovers every function directory and was already correct.
4. **A "Payment via Stripe" label and a literal `stripe` badge were hardcoded** in both billing dashboards regardless of which gateway is actually active. Both now render the real active gateway.
5. **The displayed INR rate ignored whether INR is actually active** in Settings → Currency. `layout.tsx` queried `currencies.exchange_rate_to_usd` for INR without checking `is_active`, so if an admin hasn't activated INR yet, the UI could show a price using a configured-but-not-live rate while the actual PAYG checkout call would reject it. The display now falls back to the same conservative default rate the backend uses in that situation, so what's shown never promises a price checkout isn't ready to charge.

I also corrected two stale code comments in `checkout/index.ts` that still called Stripe "the default" after the flip, and added the missing `RAZORPAY_PLAN_STARTER`/`_CREATOR`/`_PRO_PLUS` lines to `.env.example` (previously only mentioned in a comment, not given their own fillable lines).

## Flow-by-flow verification

**Subscription checkout.** `createRazorpaySubscriptionCheckoutSession()` creates a RazorPay Subscription via the Plan ID for the requested tier, records a `subscriptions` row up front (status `unpaid`, so the webhook has something to resolve onto immediately), and returns `razorpay_subscription_id` + `razorpay_key_id` for the frontend to open RazorPay Checkout.js with — deliberately not RazorPay's own hosted `short_url`, which strands the user on `api.razorpay.com` with no way back, exactly as AutoGPT's own code documents. The actual tier grant happens only in the webhook, never from this response. A user with an existing active RazorPay subscription is blocked from starting a second one (409), matching the documented "cancel before switching tiers" limitation of RazorPay's proration model.

**PAYG top-up.** `createRazorpayPaygOrder()` reads the live INR rate from the `currencies` table (throwing, not guessing, if INR isn't configured or active — this is the exact fail-safe AutoGPT's own platform didn't have, and which caused a real ~89x over-crediting bug in AutoGPT's history), converts the requested credits to paise at that rate, and stores the credited amount directly in the RazorPay order's `notes.credits` so the webhook never has to re-derive it from a rate that might have changed by the time payment settles.

**Webhook processing.** `webhook-razorpay/index.ts` verifies the `X-Razorpay-Signature` header with a proper timing-safe HMAC-SHA256 comparison before parsing the body at all, fails closed if the webhook secret isn't configured, and dedupes by a SHA-256 hash of the raw body (RazorPay doesn't provide a stable delivery ID the way Stripe does). `subscription.activated`/`.charged` initializes or resets the user's monthly credit allowance using the same `reset_monthly_credits` RPC the Stripe path already relies on. `subscription.cancelled`/`.completed`/`.halted` downgrades to free without clawing back credits already granted. Any handler error is dead-lettered (not silently dropped) while still returning 200 to RazorPay, so RazorPay doesn't retry-storm a transient failure.

**Double-credit check on PAYG payments.** RazorPay sends `order.paid` and `payment.captured` as two separate webhook deliveries with different bodies for the same underlying payment — the SHA-256 body-hash dedup above does *not* catch this, since the bodies differ. I confirmed against RazorPay's own webhook documentation that both events carry the same `payment.entity.id`, and `handlePaygOrderPaid()` uses exactly that ID as the crediting key. The `add_purchased_credits_razorpay` database function is the real safety net: it takes a Postgres advisory lock keyed on the RazorPay payment ID and checks for an existing `credit_transactions` row with that ID before crediting anything, returning a no-op `duplicate: true` result on the second call. So a user is protected from double-crediting even though two separate webhook events fire for one payment.

**Cancellation.** `cancel-subscription/index.ts` branches on each subscription row's own recorded `payment_gateway`, not on today's globally active gateway — correct, since a user who subscribed under one gateway should always be cancelled through that same gateway even after an admin later switches the default. An already-cancelled/expired RazorPay subscription is treated as a successful cancel rather than surfacing an error.

## Currency display accuracy — one thing to know

PAYG top-up pricing is exact: the same admin-configured INR rate is used both to compute the displayed price and to compute the actual paise amount charged at the moment of purchase, so what's shown is what's charged.

Subscription tier pricing is a **display estimate**, not the authoritative price. RazorPay has no per-request pricing the way Stripe's Checkout does — the actual monthly charge is fixed by whatever amount was configured on the RazorPay Plan when it was created in the RazorPay dashboard. Vantly computes the displayed INR figure as `usdBasePrice × configured_exchange_rate` at render time, purely for display. If the RazorPay Plan's real price and the configured exchange rate drift apart — the rate is updated but the Plan isn't, or vice versa — the displayed subscription price and the amount RazorPay actually charges will disagree. AutoGPT's own platform sidesteps this by hardcoding separate fixed INR figures per tier (with a database override), rather than computing a live conversion; Vantly's approach is more automatically responsive to currency-rate changes but carries this drift risk specifically for subscription tiers, not PAYG. Worth checking that the Plan's real price and the configured rate agree after setup, and again after any future rate change.

## A known duplication worth knowing about, not fixed

`checkout/index.ts` has two separate PAYG pack definitions: `getPaygPacks()` (local to that file, Stripe-shaped, used for both the Stripe price lookup and — for its `credits` field only — the RazorPay pack lookup) and `PAYG_PACKS` in `_shared/plans.ts` (the newer canonical definition, also used elsewhere). Both currently agree (`pack_3900` → 3,900 credits in both places), so there's no active bug, but a future change to one without the other would silently desync the credited amount from what's charged. I didn't merge them this session since doing so means touching the working Stripe code path, which the existing code deliberately avoids disturbing. Worth a follow-up cleanup at some point, not urgent.

## Everything checked mechanically

A full `tsc --noEmit` across the entire `apps/web` Next.js project came back with zero errors. The Deno Edge Functions (`checkout`, `webhook-razorpay`, `cancel-subscription`, `billing-history`, `webhook-stripe`, and every `_shared/*.ts` module they import) were typechecked with the project's bundled TypeScript compiler configured to mimic Deno's module resolution; the only errors reported were the two expected classes that come from checking Deno code outside the Deno runtime itself — "Cannot find name 'Deno'" and "Cannot find module 'https://esm.sh/...'" — nothing else. Every file touched this session was confirmed to have balanced braces, parens, and brackets. The new migration (`supabase/migrations/20260904140000_razorpay_billing.sql`) uses `IF NOT EXISTS`/`CREATE OR REPLACE`/`DROP POLICY IF EXISTS` throughout, so it's safe to apply even if it's accidentally run more than once. The Content-Security-Policy in `apps/web/middleware.ts` allows RazorPay's checkout script, API, and logging domains (`checkout.razorpay.com`, `api.razorpay.com`, `lumberjack.razorpay.com`) in `script-src`, `connect-src`, and `frame-src` respectively, so Checkout.js won't be silently blocked by the browser once real keys are in.

## Before entering real keys

A few things need to happen in this order for RazorPay to actually work once keys are in, beyond just setting the keys themselves:

- Run the new migration (`20260904140000_razorpay_billing.sql`) and the pending `20260904130000_admin_settings.sql` change (adds the seeded INR currency row) against the database, if they haven't been applied yet.
- Activate INR in Settings → Currency and set the exchange rate you actually want to charge at. It's seeded `is_active=false` by default — PAYG checkout will refuse to charge in INR until this is turned on (this is intentional fail-safe behavior, not a bug), and the price display will show the fallback rate rather than your configured one until it's active.
- Create each paid tier's Plan (Starter/Creator/Pro Plus) in the RazorPay dashboard ahead of time, and put its Plan ID into `RAZORPAY_PLAN_STARTER`/`RAZORPAY_PLAN_CREATOR`/`RAZORPAY_PLAN_PRO_PLUS` as a Supabase Edge Function secret (not needed on the web container). A tier left unconfigured simply can't be subscribed to yet — it doesn't block the other tiers or PAYG.
- Set `RAZORPAY_API_KEY`, `RAZORPAY_API_SECRET`, and `RAZORPAY_WEBHOOK_SECRET` in **both** places: as Supabase Edge Function secrets (`supabase secrets set ...`) and in the web container's own env file (`.env.local`/`.env.prod`, loaded via `env_file` in `docker-compose.yml`). These are two independent systems that happen to read the same variable names — set in only one place, the other silently behaves as if RazorPay isn't configured at all.
- Set `PAYMENT_GATEWAY=razorpay` explicitly in both of those same places too, even though it's now the code default — an explicit value is safer than relying on the default once you're depending on it in production, and keeps things obvious if you ever revisit this config.
- If you'd rather stay on Stripe for now and flip to RazorPay later, set `PAYMENT_GATEWAY=stripe` in both places instead — nothing else needs to change.

Once those are in place, a real end-to-end test would be: a Starter-tier subscription checkout, a PAYG top-up, and a subscription cancellation, watching each land correctly in `subscriptions`, `user_credits`, `credit_transactions`, and `razorpay_webhook_events`.
